# Codex: one-shot план изменения прототипа «Тариф»

## Цель

Изменить существующий прототип в репозитории `hoseantonio85-art/tarif-planes-copy` по зафиксированным бизнес-требованиям, используя `@sber-orm/ui-kit@0.283.0` и правила frontend-разработки.

Не создавать новый прототип и не делать глобальный редизайн. Сохранить существующий светлый каркас, sidebar, общую ширину страницы и визуальную логику продукта. Переработать только страницу тарифа, связанные с ней компоненты, данные и состояния доступа.

---

# 1. Как работать

Это задание должно быть выполнено как одна цельная работа, а не как цепочка мелких промптов.

## До изменения кода

1. Прочитать обязательные источники из раздела 2.
2. Провести короткий preflight текущего репозитория.
3. Создать в проекте файл:

```text
docs/tariff-implementation-plan.md
```

4. Записать в него:
   - затрагиваемые файлы;
   - дерево компонентов;
   - модель данных и владельцев состояния;
   - карту `элемент интерфейса → компонент UI Kit`;
   - список удаляемого legacy;
   - scenario matrix;
   - порядок реализации;
   - проверки и Definition of Done.
5. После создания файла **сразу выполнять этот план**, не ожидая отдельного подтверждения пользователя.

## Уточнения

Не задавать вопросы по одному.

Задать не более **одного объединённого вопроса** только тогда, когда обнаружен настоящий blocker, без которого реализация невозможна. Например:

- отсутствует пакет UI Kit;
- фактический API пакета несовместим с проектом;
- repository instructions запрещают необходимое изменение;
- не удаётся сохранить текущий runtime или маршрутизацию.

Некритичные пробелы записать в раздел `Допущения` файла-плана и продолжить работу.

# 3. Бизнес-требования

## BT-01. Верх страницы

Показать две карточки в одну строку, одинакового визуального веса.

### Левая карточка

```text
Тариф
Базовый
Период действия
```

В данных периода показать фактические даты, например:

```text
01.02.2026–31.12.2026
```

### Правая карточка

```text
Статус договора
Активен
Номер договора
```

В данных номера показать фактическое значение, например:

```text
Договор № 452-26С
```

### Запрещено добавлять в карточки

- описание тарифа;
- счётчик X/Y;
- progress bar;
- кнопки и CTA;
- предупреждения;
- дополнительные метрики.

Информацию из этих карточек не повторять отдельным блоком ниже.

---

## BT-02. Компании в рамках договора

После верхних карточек показать блок:

```text
Компании в рамках договора
```

Требования:

- показать все компании;
- в текущих данных максимум 6;
- текущую компанию можно отметить нейтральным статусом `Текущая`;
- блок только для чтения;
- без добавления, удаления и редактирования компаний.

---

## BT-03. Доступные модули

Следом показать:

```text
Доступные модули
```

Требования:

- компактное отображение без сложной композиции;
- по клику на модуль открывать `Popover`;
- внутри показывать название;
- показывать описание, когда оно заполнено;
- показывать действие `Перейти в сервис`;
- модель данных должна поддерживать отсутствие описания.

Если модуль входит в тариф, но недоступен текущему пользователю по роли:

- объяснить это в popover;
- не давать активный переход.

Не реализовывать:

- подключение модуля;
- покупку модуля;
- изменение тарифа.

---

## BT-04. Счётчик пользователей

В блоке пользователей показать:

```text
Активные платные пользователи — X из Y
```

Считать только пользователей:

- со статусом `active`;
- у которых есть платная роль.

Платные domain role ids:

```text
ORMCLOUD_RISKMANAGER
ORMCLOUD_USER
```

Не использовать русское название роли в бизнес-условиях.

---

## BT-05. Строка фильтрации

Сделать компактную строку по принципу приложенного референса.

### Слева — быстрый фильтр

```text
Все
В тарифе
Не в тарифе
```

Использовать один компактный segmented/radio control.

### Справа

- icon-only кнопка поиска;
- кнопка `Фильтр` с иконкой.

### Поиск

После нажатия на иконку под основной строкой появляется поле поиска на всю ширину.

Искать по:

- ФИО;
- email;
- роли.

### Полный фильтр

Открывать в компактном `Popover`.

Минимальный состав:

- активен / деактивирован;
- роль;
- не заходил более 2 месяцев.

Действия:

- `Сбросить`;
- `Применить`.

Не добавлять большой отдельный экран фильтров.

---

## BT-06. Список пользователей

В строке показать:

- ФИО;
- email через tooltip и копирование;
- приоритетную отображаемую роль;
- признак `В тарифе` или `Не в тарифе`;
- дату последнего входа;
- сигнал `Не заходил более 2 месяцев`;
- статус доступа;
- switch для edit-роли.

Деактивированного пользователя не удалять из списка. Строку приглушить, сохранив читаемость.

Если у пользователя несколько ролей:

1. приоритет имеет платная роль;
2. затем используется стабильный priority mapping;
3. display label не участвует в business logic.

---

## BT-07. Управление пользователем

### Деактивация

При выключении switch:

1. не менять данные сразу;
2. открыть modal подтверждения;
3. показать имя пользователя;
4. сообщить, что доступ будет закрыт, а история сохранится;
5. действия: `Отменить`, `Деактивировать`.

После успеха обновить строку и X/Y.

### Активация платного пользователя

Если `X < Y`:

- активировать;
- увеличить X;
- показать success feedback.

Если `X = Y`:

- не менять switch;
- открыть modal `Достигнут лимит активных пользователей`;
- показать X/Y;
- объяснить необходимость сначала деактивировать другого платного пользователя;
- действие: `Понятно`.

Не показывать покупку лицензий.

### Активация пользователя не в тарифе

- активировать;
- X/Y не менять;
- modal лимита не показывать.

### View-only

Пользователь с view-only permission:

- видит страницу и список;
- не может переключать статусы;
- switch скрыт или disabled.

---

## BT-08. Состояния доступа ко всей системе

Эти состояния показывать вместо продуктового интерфейса, без sidebar и данных компании.

### `pending_provisioning`

```text
Мы готовим ваш доступ

Учётная запись создаётся. Когда доступ к NORM будет готов,
мы отправим уведомление на вашу почту.

Если уведомление не придёт, обратитесь в службу поддержки.
```

Действия:

- `Написать в поддержку`;
- `Выйти`.

### `deactivated`

```text
Доступ приостановлен

Ваша учётная запись деактивирована.
История действий и данные сохранены.

Для восстановления доступа обратитесь к администратору компании
или в службу поддержки.
```

Действия:

- `Написать в поддержку`;
- `Выйти`.

### `provisioning_failed`

Recoverable error:

- понятное сообщение;
- `Проверить ещё раз`;
- `Написать в поддержку`.

Не обещать конкретный SLA.

# 5. Технические границы

В перерабатываемом scope:

- использовать `@sber-orm/ui-kit`;
- layout — через `Row`/`Col`, где это обычная раскладка;
- типографика — `Title`/`Text`;
- новые стили — colocated `styles.module.scss`;
- пользовательские строки — i18n;
- domain ids — стабильные, не локализованные;
- mock data — отдельно от page/components;
- бизнес-вычисления — selectors/helpers/model;
- helpers и store/model transformations — с тестами;
- внутренние импорты — через `@/`;
- компонент больше 400 строк запрещён;
- route-level page содержит только composition/orchestration.

В перерабатываемом scope не использовать:

- shadcn;
- Radix;
- lucide;
- Tailwind palette/arbitrary utilities;
- hardcoded colors;
- локальные UI-фасады, имитирующие UI Kit.

Legacy вне scope не переписывать без необходимости.

Не добавлять MobX, если его нет в runtime проекта. Сохранить существующий способ управления состоянием либо выделить model hook и чистые selectors.

Обязательная структура:

```md

## 1. Scope
Что меняем и что не меняем.

## 2. Файлы
| Файл | create/update/delete | Назначение |

## 3. Component tree
Краткое дерево страницы.

## 4. Data model and state
Domain ids, fixtures, derived values, владельцы состояния.

## 5. UI Kit map
| Элемент | Реальный компонент UI Kit | Проверенный API |

## 6. Scenario matrix
Default, limit reached, view-only, stale, pending provisioning,
deactivated, provisioning failed, module unavailable.

## 7. Порядок реализации
6–10 последовательных шагов.

## 8. Проверки
Команды и acceptance checklist.

## 9. Допущения
Только неподтверждённые, но неблокирующие решения.
```

После записи этого файла Codex должен работать по нему и обновлять статусы шагов по мере выполнения.
